Loading, empty, and error states

A network request can be slow, return nothing, or fail. A good interface tells the truth at every moment. Learn to model four states and render them without guessing.

Name the four states

Most data-driven interfaces have four states. If you only build the success state, every slow request looks broken and every failure looks frozen.

StateMeaningWhat the user sees
LoadingThe request is still running.A short status message or skeleton; controls disabled.
EmptyThe request succeeded but found nothing.A clear "no results" message with a next step.
ErrorThe request failed or timed out.A plain-language message and a retry action.
SuccessData arrived and is ready.The actual content, rendered from the data.

There is also a fifth, quieter state: idle, before the first request. Treat it as "nothing has happened yet" and show a short instruction. Do not reuse the empty message; "no results" is confusing before a search.

Render from one state object

Keep the state in one object and let a single render() function decide what the screen shows. The UI becomes a function of the state, not a pile of unrelated DOM changes.

Every transition goes through setState(): set loading, then success, empty, or error. That gives you one place to update the screen and one place to debug.

Clear stale data

When a new request starts, decide whether to keep the old result visible. For a small weather card, clearing it avoids showing yesterday's temperature next to a loading message.

Catch errors and show something useful

Wrap the request in try/catch. Throw your own error when response.ok is false. Log the technical detail for yourself, but show the user a message they can act on.

The timeout uses an AbortController. When the timer fires, controller.abort() cancels the request and the catch block sees an error named AbortError. The finally block clears the timer whether the request succeeds or fails.

A retry button should call the same load() function with the last city. Disable it while loading so a double click does not start two requests. If the failure is a 404, a retry will not help; tell the user to change the search instead.

Do not swallow the error

An empty catch block hides the bug and leaves the user staring at a blank screen. Always move the UI into an error state and log the original error for debugging.

Announce changes with aria-live

Screen reader users do not see a spinner appear. Mark the status area as a live region so changes are announced without moving focus.

role="status" already implies a polite live region. Keep the region small: put the changing message inside it, not the whole page. Avoid aria-live="assertive" for routine loading updates, because it interrupts whatever the user is reading.

When an error appears, make sure the message is visible and in the live region. If a retry button appears, give it a real label such as "Try again", not an icon with no accessible name.

Check yourself

What is the difference between the empty and error states?

Empty means the request worked but returned no matching data, such as an unknown city. Error means the request did not complete correctly. Empty usually asks for a different search; error usually offers a retry.

Why clear the timeout in a finally block?

The timer should not fire after a fast response. finally runs on both success and failure, so it is the reliable place to cancel the pending timeout and avoid a stray abort later.

Key things to remember

  • Model the state, then render it. Loading, empty, error, and success should each have a designed screen.
  • Failures need a next step. Show a plain-language message, log the technical error, and offer retry when it can help.
  • Announce changes. A small polite live region keeps screen reader users informed without stealing focus.
