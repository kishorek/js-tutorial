State and rendering lists

Lists get messy when every click edits the page directly. Keep the truth in a small state array, write one render function, and let every action flow through the same path.

Lesson 5.3 60–75 min Beginner

By the end, you can

  • Store list data in a state array of objects.
  • Render that array with a single function.
  • Add, toggle, remove, and filter items safely.

You need

  • Lesson 5.1 and 5.2 completed.
  • Comfort with map and filter.
  • A page with a list, a form, and an empty container.

State first, then render

State is the data the screen depends on. For a list, that is an array of objects. Do not treat the visible list items as the source of truth; they are only one rendering of the array.

Every change follows the same three steps: update the state, call render, and let the screen catch up. The render function never decides what is true; it only describes the current array.

Why start over

Clearing and rebuilding a short list is fast and predictable. It removes a whole class of bugs where one row is updated but another is left stale. For very large lists, update individual nodes later.

Add, toggle, and remove

An id connects a button in the DOM to one object in state. Put it in a data-id attribute and read it with dataset.id. Remember that attribute values arrive as strings. Each rendered row also needs a button with data-action set to toggle or remove; the exercise builds that complete row.

One listener on list still works after every render because it listens on the parent, not on the buttons. filter creates a new array without the removed item; map creates a new array with one object replaced. Both then feed the next render.

User text goes into the DOM with textContent, never through an HTML string. If an item's text contains <b>, the visitor should see the characters, not bold text.

Empty states and filters

A filter is state too. Store the current choice in a variable, build the visible subset, and render that subset. An empty result deserves a message instead of a blank box.

When the filter button changes, set the variable and call the render function again. Keep the empty message in the same list so the layout does not jump to a separate element.

Render, add, and toggle a list

Assume the page has <ul id="list">, <form id="add-form">, and <input id="new-item">. Start with an array of two objects. Render every item with a text span and a toggle button, show an empty message when the array is empty, add a trimmed item on submit, and toggle done with one delegated click listener.

Make an attempt first. Then the model answer unlocks.

Check yourself

Why rebuild the whole list instead of changing one row?

A full render always matches the state array, so filters, counts, and empty messages cannot drift out of sync. It is also less code to maintain for small lists.

Why use an id instead of the item's position?

Positions change when an item is removed or filtered out. A stable id still points to the right object after the array is rebuilt.

Key things to remember

  • State is the source of truth. The DOM is a projection of the array, not the array itself.
  • Change state, then render. One path for add, toggle, remove, and filter keeps behaviour predictable.
  • Use ids and textContent. Data attributes connect controls to items; plain text keeps user input safe.
