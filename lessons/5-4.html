The brief

Both apps use the same loop from Lesson 5.3: change the data, call render, and let the DOM catch up. Build the to-do list first. The quiz is a second page that repeats the pattern with a different shape of state.

FeatureRequirement
AddTrim the text, ignore an empty value, clear the input, and keep focus there.
ToggleMark one item done and update the remaining count.
DeleteRemove only the chosen item; keep the rest of the array intact.
FilterShow all, active, or done items, with a clear empty message.
QuizStore questions in an array, track a score, and reset both.

Build the to-do app

The starter already has the markup and a little CSS. Your job is the state, the render function, and the listeners. Use one delegated click listener for toggle and delete, and one submit listener for adding.

Add the quiz screen

Use a second page with <div id="quiz"></div>. Keep the questions in an array, track the current index and score, and render one question at a time. The reset button returns both numbers to zero.

Accessibility and behavior

  • Every input has a label; every icon-only button has an accessible name.
  • Use type="button" on buttons that should not submit a form.
  • Keep focus visible and return it to the input after adding an item.
  • Announce the remaining count with aria-live="polite".
  • Never insert user text with innerHTML; set it with textContent.
  • Test with the keyboard only: add, toggle, delete, filter, and reset.

Common questions

Should the to-do list save after refresh?

Not yet. Persistence arrives with localStorage in Module 6. For now, keep state in memory and let the starter array provide sample data.

Why use a template string for the list markup?

The template holds only trusted structure and numeric ids. The visitor's text is still inserted separately with textContent, so it cannot become markup.
