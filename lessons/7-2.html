Accessibility and performance audit

A site that only works with a mouse and a fast connection is a site that loses people. Run the same audit every time: keyboard, focus, contrast, labels, images, motion, and the bytes you ask visitors to download.

Lesson 7.2 60–75 min Intermediate

By the end, you can

  • Run a keyboard and screen-reader sanity check.
  • Find and fix the most common WCAG failures.
  • Cut avoidable layout shift and download weight.

You need

  • A page you built in this course.
  • Chrome DevTools and Lighthouse.
  • Ten minutes with the keyboard only.

Access is a baseline

WCAG is the Web Content Accessibility Guidelines. Aim for level AA, not perfection. The four principles are easier to remember as POUR: content must be perceivable, operable, understandable, and robust. In everyday code that means six habits.

  • Keyboard first. Every link, button, field, and menu must work with Tab, Shift+Tab, Enter, Space, and the arrow keys where expected.
  • Visible focus. Never remove the focus outline without replacing it. A clear ring tells keyboard users where they are.
  • Contrast. Body text needs at least 4.5:1 against its background. Large text and interface boundaries need at least 3:1.
  • Names. Every input has a real label. Every meaningful image has useful alt text. Decorative images use alt="".
  • Structure. Use one main, a logical heading order, and landmarks such as header, nav, and footer. Add a skip link.
  • Motion. Respect prefers-reduced-motion and never make an animation the only way to understand something.
Overlays are not a fix

An accessibility widget cannot repair a div pretending to be a button, an unlabeled input, or unreadable contrast. Fix the HTML and CSS at the source.

Run the same audit every time

Print this checklist or keep it beside your editor. A full pass takes about fifteen minutes on a small site.

Test with a keyboard, not a checklist

Put the mouse away and complete the main task. If you cannot see where focus went, a keyboard user cannot either. Then try a screen reader for five minutes; VoiceOver, NVDA, and TalkBack are free.

Performance is part of the experience

Performance is accessibility for slow devices and unreliable networks. Start with the largest visible image, the fonts, and the JavaScript.

  • Reserve image space. Set width and height so the layout does not jump when the file arrives.
  • Lazy-load below the fold. Use loading="lazy" for images further down. Do not lazy-load the hero image; it hurts the largest contentful paint.
  • Make fonts swap. Use font-display: swap, load only the weights you use, and prefer one family.
  • Ship less JavaScript. Remove unused libraries, defer scripts, and check the Network panel for files that are larger than they need to be.
  • Measure on mobile. Run Lighthouse with the mobile setting and a throttled connection. A desktop score is not the score your visitors get.
Scores are a smoke alarm

A perfect Lighthouse score does not prove the page is accessible. Automated tools catch only part of the problem; keyboard testing and human judgment catch the rest.

Check yourself

Does a Lighthouse score of 100 mean the page is accessible?

No. Automated tests catch some missing names, contrast failures, and structural issues, but they cannot judge whether the keyboard order makes sense or whether a screen-reader experience is clear. Test the real interaction.

Why not add loading="lazy" to every image?

Lazy loading delays the image until the browser thinks it is needed. On the hero or largest above-the-fold image that can make the page feel slower. Use it for images below the fold.

Key things to remember

  • Keyboard, focus, contrast, labels, alt, landmarks. Run the same six checks on every page.
  • Performance is user experience. Reserve space, compress images, and question every kilobyte of JavaScript.
  • Audit with people, not only scores. Automated tools start the conversation; real use finishes it.
